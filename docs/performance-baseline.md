# Audit performance baseline

Measured before any optimization (branch `perf/audit-baseline-profiling`, code identical to
`main` at 0737a3f). All data is **synthetic**, generated by `benchmarks/synthetic_export.py`
(seed 1, profile `realistic`: 30-180 min sessions at 1 Hz, GPS/HR/speed/distance/cadence/
power/altitude depending on sport, laps, plus deliberate defect files). No private Polar
exports were used. Spec: [SPEC-003](../specs/003-audit-performance.md).

## Reproduce

```text
python benchmarks/synthetic_export.py <dir> --count 96 --seed 1 --profile realistic
python benchmarks/run_audit_benchmark.py <dir> --work <scratch> --label baseline --warm-runs 2 --json result.json
python benchmarks/stage_profile.py <dir> --limit 3 --profile-top 20
```

`run_audit_benchmark.py` runs `main.py audit` in a fresh subprocess and measures the whole
process tree (Windows Job Object; `getrusage` elsewhere): wall, CPU, peak memory, I/O, plus
SHA-256 fingerprints of manifests, FIT files and a timing-free projection of the audit report.
*Cold* = empty output directory; *warm* = rerun into the same directory (existing FITs are
fully re-validated, status `skipped_existing`).

## Environment

Windows 11, 16 logical CPUs, Python 3.12.10, fit-tool 0.9.16, local SSD. Audit uses 8 workers
(hard cap). 96 files, 147 MB total (1.5 MB average); 94 valid, 1 malformed JSON, 1 missing
timezone (`requires_configuration`).

## Results (96 activities)

| Run | Wall | Activities/s | CPU user+kernel | Peak tree memory | Read / write MB | Processes |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| cold | 146.5 s | 0.66 | 1107 s | 4494 MB | 696 / 11.7 | 10 |
| warm 1 | 72.2 s | 1.33 | 517 s | 3036 MB | 696 / 0.9 | 10 |
| warm 2 | 76.8 s | 1.25 | 530 s | 3169 MB | 696 / 0.9 | 10 |

Roughly 11.5 CPU-seconds per activity cold and 5.4 warm, about 7.6x the CPU time of wall time
at 8 workers: the work is CPU bound in workers, not I/O bound. Extrapolated to 2,928
activities of this size: about 74 min cold on this machine (the reported real audit took
45m 03s with different data and hardware; compare ratios, not absolutes).

Cold and warm runs produce identical `migration-manifest.json/.csv`,
`migration-config.template.json` and identical FIT bytes (fingerprints equal). The
timing-free audit projection differs only because warm rows are `skipped_existing` instead
of `converted`, so before/after comparisons must compare cold-to-cold and warm-to-warm.

## Where the time goes (single process, 3 activities, 1.25 MB average)

| Stage | s/activity | Share |
| --- | ---: | ---: |
| `FITBuilder.build`: encode + internal decode/verify round trip | 4.47 | 60.8% |
| `_decode_fit`: second full decode of the written file | 2.73 | 37.0% |
| `import_activity` (JSON load, parse, laps) | 0.107 | 1.5% |
| `_domain_counts` + `_warnings` | 0.018 | 0.2% |
| `_source_info` + `_source_metadata` (two extra JSON loads) | 0.022 | 0.3% |
| source/FIT SHA-256, validate, write | 0.006 | <0.1% |

cProfile attributes about 6.2 of 10.8 profiled seconds to `fit_tool` decoding (two decodes of
about 3.1 s each); roughly 1 M `fit_tool.field.Field` objects are constructed per large file.
`tracemalloc` peak is 280 MB for one activity, which explains the ~4.5 GB tree peak with
8 workers.

## Conclusions

1. Decode, not parsing/hashing/JSON/reporting, is the bottleneck (about 98%). JSON-level
   optimizations (single parse, orjson, lap indexing) cannot exceed ~3% gain.
2. Removing the redundant second decode on freshly generated files is worth ~37% with no
   change to checks (SPEC-003 D1). Worker cap and chunking affect ~1.0-2.0x depending on
   cores; memory must be bounded (SPEC-003 AC-04).
3. A 3x cold-run improvement is **not** reachable without either a faster verified decoder or
   more workers; honest expectation for approved low-risk changes: ~1.6x cold (single decode)
   times up to ~2x from workers on 16 cores (memory permitting). Warm 3x+ is reachable only
   with the hash-keyed incremental cache (SPEC-003 D2).
4. The remaining ranked bottleneck after D1 is `fit_tool` message decoding (`Field.__init__`,
   `definition_message.get_field`), addressed only by D3 (out of scope without differential tests).

## After SPEC-003 (same data set, same machine)

Changes: single decode of generated FIT (D1), worker default = CPU count within a memory
bound (D4), initializer-based worker setup with a bounded ordered window, atomic outputs,
opt-in `--incremental` cache (D2). Measured with the same harness (`-- --incremental` passes
the flag to `audit`).

| Run | Wall | Activities/s | CPU | Peak tree memory | Speed-up vs baseline |
| --- | ---: | ---: | ---: | ---: | ---: |
| cold (default) | 64.4 s | 1.49 | 786 s | 7585 MB | **2.27x** (146.5 s) |
| warm, full verification | 41.2 s | 2.33 | 501 s | 5667 MB | **1.75x** (72.2 s) |
| cold, `--incremental` (cache written) | 49.8 s | 1.93 | 662 s | 7814 MB | 2.94x (noise vs default cold) |
| warm, `--incremental` (all cache hits) | 1.24 s | 77.5 | 1.7 s | 145 MB | **58x** (vs full warm 72.2 s) |

Interpretation:

- **3x cold target:** not reached by default (2.27x; the incremental cold run measured 2.94x,
  but cold runs differ only by noise, so treat both as ~2.3-2.9x). CPU time fell 29%
  (1107 s to 786 s); the rest is parallelism (8 to 16 workers). The remaining cost is
  `fit-tool` decoding of the single verification pass; going further needs a different
  verified decoder (SPEC-003 D3, deliberately out of scope).
- **Memory:** peak tree memory rose from 4.5 GB to 7.6 GB because 16 workers run instead of 8
  (about 470 MB per worker). Workers are capped by available memory (700 MB estimate each) and
  `--workers N` restores any lower setting.
- **Warm incremental** re-verifies only that each FIT's SHA-256 and size equal the values
  recorded when it was fully verified for the same source, override and code version.
- **Equivalence:** manifest JSON/CSV, configuration template, every FIT byte and the
  timing-free audit report projection are identical to the baseline for default cold,
  default warm, incremental cold and incremental warm runs (fingerprints in the result JSON).
